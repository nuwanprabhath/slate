# End-to-end encryption — design and implementation plan (v2)

Status: v2, revised after an independent Opus security review of v1 (2026-10-23). Changes from v1 are
summarised in §14.

## 1. Goal and the maintainer's decisions

Encrypt every note on the device and in the sync remote (git repo or OneDrive), so that only someone who knows
the user's password (or holds the recovery key, or unlocks with an opt-in quick unlock on a device where they
enabled it) can read them. Existing users opt in from Settings → Security; their data is migrated in place.

| Topic | Decision |
| --- | --- |
| Unlock | Password (root secret) + a recovery key shown once. Opt-in quick unlock: Touch ID on macOS, "remember in the system keyring" on Linux (Electron `safeStorage`). |
| In-app WebAuthn passkeys | Not possible for an unsigned Electron app. Out of scope. |
| Lock timing | Unlock at every launch. Lock after Slate has had no input for the idle time (Settings; default 30 min; "never" allowed), on system sleep, on screen lock where the OS reports it, and on "Lock now" (menu + Mod+Shift+L). |
| Old plaintext git history | Wiped: after confirmation the remote branch is replaced by one encrypted commit (force push with lease). |
| MCP (AI) access | Only while Slate runs and is unlocked; `slate-mcp` becomes a stdio↔socket proxy to the app. |

Non-goals (stated in the UI and README): malware running as the user while Slate is unlocked; hiding counts,
sizes and timing from the sync provider; re-encrypting everything under a new master key (v1; §11); turning
encryption back off (v1).

## 2. Threat model

Protected:
- **T1 Remote compromise** (repo or OneDrive read, from now on): no note content, titles, names, images, search
  text, device names or document kinds. Forged or altered files are rejected.
- **T2 Device at rest** (off, or Slate closed/locked): nothing *Slate writes after migration* in its data folder
  reveals note content.
- **T3 Offline guessing**: Argon2id with enforced floors and a password minimum.
- **T4 Malicious remote content**: a hostile remote cannot write outside the sync folder (symlinks), crash the app
  (huge KDF params, huge files), stop sync permanently, or silently lock the user out.

Not protected (documented in the wizard and README):
- An attacker in the user's logged-in session while Slate is unlocked. A same-user process can also read the
  quick-unlock secret from the keychain.
- Copies made before migration: Time Machine / Déjà Dup backups, APFS/btrfs snapshots, SSD remapping, git or
  OneDrive history held elsewhere. Overwriting old files is not attempted, because it is futile on copy-on-write
  filesystems. The wizard recommends FileVault or LUKS and pruning old backups.
- Swap and hibernation images, and core dumps (we disable core dumps for the process where possible: `ulimit` is
  not available from Electron; Crashpad is not enabled in Slate and must stay off).
- Deletion or rollback of whole remote files by someone with write access; §5.5 limits the damage.

## 3. Keys

```
password (NFC) ──Argon2id(salt, params)──▶ KEK_pw ─┐
recovery key (256-bit) ──HKDF──────────────▶ KEK_rc ─┼─ AES-256-GCM wrap ──▶ MK   (account master key, 256-bit random, shared by all devices)
quick-unlock secret (safeStorage) ──HKDF───▶ KEK_qu ─┘   (per device, optional)

MK ─HKDF─▶ K_localwrap  info "slate/v1/local-wrap"   wraps this device's LK (below)
   ─HKDF─▶ K_sync       info "slate/v1/sync"         remote file envelopes (per-file subkeys, §5.3)
   ─HKDF─▶ K_name       info "slate/v1/name"         HMAC key for remote folder and blob names
   ─HKDF─▶ K_check      info "slate/v1/check"        vault header MAC (§4)
   ─HKDF─▶ K_prefs      info "slate/v1/prefs"        MAC of preunlock.json (§6.6)

LK (per device, 256-bit random) ── the SQLCipher key of this device's database; stored only wrapped:
   local-keys.json = { vaultId, deviceId, nonce, ct = GCM(K_localwrap, LK, AAD = "slate-lk/v1|" + vaultId + "|" + deviceId) }
```

- **LK is random per device** and stored wrapped under MK, so the database can be opened before anything is read
  from it, and joining another vault (§7.4) only rewraps LK — no `PRAGMA rekey`, no re-encryption.
- **Argon2id** via `hash-wasm` (pure WebAssembly; Node's `crypto.argon2Sync` is unavailable in Electron because
  Electron's Node uses BoringSSL — verified). New dependency: `hash-wasm@4.12.0`. Runs in a `worker_thread`.
  Parameters: memory 256 MiB, passes 3, parallelism 1 (wasm is single-threaded; parallelism is part of the hash, so
  it is fixed at 1), 32-byte output, 16-byte salt. Calibrated once at vault creation: if it takes > 3 s use
  128 MiB × 4.
  - **Floors** (refuse below): memory ≥ 64 MiB, passes ≥ 2, salt ≥ 16 B. **Ceilings** (refuse above, checked
    *before* deriving, from any source): memory ≤ 1 GiB, passes ≤ 10, parallelism = 1, salt ≤ 64 B.
  - Known-answer tests with RFC 9106 vectors (adjusted to what hash-wasm supports).
- **Passwords** are normalised to Unicode NFC before hashing. Minimum 10 characters; refused if in a bundled top-10k
  common-password list; a length/class strength hint. No new dependency.
- **Recovery key**: 32 random bytes → 52 Crockford base32 characters + a 4-character checksum (first 20 bits of
  SHA-256 of the 32 bytes) = 56 characters in **14 groups of 4**. Input ignores case, spaces, dashes and maps
  O→0, I/L→1. `KEK_rc = HKDF(recovery, salt = vaultId, info = "slate/v1/recovery")`.
- **Key handling in memory**: keys live only in the main process in a `KeyRing` object. `KeyRing.close()` makes
  every accessor throw `Locked` afterwards and then zeroes its buffers (best effort: the hex string passed to
  `PRAGMA key` and the password string cannot be zeroed, and the UI makes no promise that memory is wiped). Code
  that needs a key calls `keyRing.get(name)` at the moment of use, never caches it, so a locked ring can never yield
  an all-zero key. The renderer never receives a key; the password crosses IPC once and goes straight to the worker.

## 4. The vault header

`vault.json` — non-secret, authenticated. Local copy in the data folder; shared copy at `e2ee/vault.json` in the
remote.

```json
{
  "format": "slate-vault", "version": 1,
  "vaultId": "<uuid>", "revision": 3, "createdAt": 1761200000000,
  "kdf": { "alg": "argon2id", "memoryKiB": 262144, "passes": 3, "parallelism": 1, "salt": "<b64>" },
  "wraps": {
    "password": { "nonce": "<b64 12B>", "ct": "<b64 48B>" },
    "recovery": { "nonce": "<b64 12B>", "ct": "<b64 48B>" }
  },
  "check": "<b64 HMAC-SHA256(K_check, JCS(header without 'check'))>"
}
```

- **Parsing before trust**: a strict schema validator runs first (exact keys, types, base64 lengths, the KDF
  ceilings/floors of §3, `revision` a positive safe integer). Only then is anything derived.
- Each wrap: AES-256-GCM of MK, AAD = `"slate-vault/v1|" + vaultId + "|" + slot + "|" + JCS(kdf)`.
- **`check`** = HMAC-SHA256 under K_check over the RFC 8785 (JCS) canonical JSON of the header minus `check`. After
  a slot unwraps MK, `check` must verify; if it does not, the unlock fails with **the same error, timing path and
  message as a wrong password** (so the GCM partitioning-oracle issue gives an attacker nothing: a key-committing
  check guards every successful unwrap).
- **`revision`** increases by 1 with every change (password change, new recovery key). A device stores the highest
  revision it has adopted and **never adopts a lower one**. It keeps no previous header: once the new one is in
  use, the old password or recovery key opens no file in the data folder (older versions' `vault.prev.json` is
  deleted). Older copies elsewhere (backups, the sync repo's history, OneDrive versions) still open with the old
  secret; full revocation would need re-encrypting everything, which this version does not do.
- **Adopting a remote header**: never silently. When the remote copy has the same `vaultId` and a higher `revision`
  and verifies under the MK we hold, the device keeps using its local header and *stores the remote one as
  pending*. The lock screen tries the password against **local, then pending**; whichever unwraps with a valid
  `check` is used, and a pending header that worked becomes the local one ("Your password was changed on another
  device" note). So a password change elsewhere never locks this device out, and a forged header (by someone with
  an old secret) is only adopted if the user's own password opens it.
- Honest UI: "Changing your password or recovery key stops the old one opening this computer's vault. Anyone
  holding an older copy of the vault files (a backup, the sync repository's history, OneDrive versions) *and* the
  old password or key can still read the notes in that copy." (§11).

## 5. Encryption formats

### 5.1 Local database: SQLCipher

- Replace `better-sqlite3` with `better-sqlite3-multiple-ciphers@13.0.3` everywhere (same API; rebuilt by
  `@electron/rebuild`). One function `openDatabase(file, key | null)` is the **only** way any code opens
  `slate.db` (app, sync, importer, CLIs, tests). With a key it runs, in order: `PRAGMA cipher = 'sqlcipher'`,
  `PRAGMA legacy = 4`, `PRAGMA key = "x'<hex LK>'"`, then `PRAGMA temp_store = MEMORY` (mandatory on every
  connection), then `SELECT count(*) FROM sqlite_master` (wrong key → "file is not a database" → `WrongKey`; no
  `CREATE TABLE` runs before this succeeds), then the existing WAL pragmas. Verified by the reviewer: WAL frames are
  encrypted, a wrong key fails cleanly; the library's default cipher is chacha20, so `cipher`/`legacy` must be set
  explicitly.
- Images move into the database when encrypted: a `blob_data (name TEXT PRIMARY KEY, mime TEXT, data BLOB)` table.
  `BlobStore` becomes an interface with the existing file implementation (plaintext users) and a DB
  implementation (encrypted users). No `.sle` files, no name mapping.
- What is readable before unlock lives in `preunlock.json` (§6.6).

### 5.2 Which database file is current

`vault.json`'s local-only companion `local-keys.json` names the encrypted database file:
`"db": "slate-<vaultId-prefix>.db"`. Plaintext users keep `slate.db`. Switching from plaintext to encrypted is the
single atomic write of `local-keys.json` (write tmp, fsync, rename, fsync dir) — no two-rename swap. `slate.db`
stays until the cleanup step and is then unlinked (not overwritten; §2).

### 5.3 Envelope for remote files

```
header = magic "SLE1" (4) | flags (1, = 0) | salt (16) | nonce (12)
fileKey = HKDF-SHA256(K_sync, salt, info = "slate/v1/remote-file")
ct|tag  = AES-256-GCM(fileKey, nonce, plaintext, AAD = header || "|" || logicalPath)
```

- A fresh salt per file gives a fresh key per file, so random nonces never collide under one key.
- `logicalPath` is the engine's path (`docs/<docId>/<deviceId>/00000001.chunk`, `blobs/<name>`,
  `devices/<id>.json`), binding each ciphertext to its place.
- Plaintext of docs and device records is deflated before encryption (no length leak beyond what sizes reveal).
- Decryption failure raises `UnverifiableFile` (§5.5); it never falls back to plaintext.

### 5.4 Remote layout: `EncryptingDrive`

`EncryptingDrive implements RemoteDrive`, wrapping `GitDrive` / `OneDriveDrive`.

| Engine path | Remote path |
| --- | --- |
| `docs/<docKey>/<dev>/<seq>.chunk` / `snapshot-<seq>.bin` | `e2ee/d/<hex HMAC(K_name, "doc|" + docId)[:32]>/<hex HMAC(K_name, "dev|" + deviceId)[:16]>/<seq>.c` / `s-<seq>.c` |
| `blobs/<sha256>.<ext>` | `e2ee/b/<hex HMAC(K_name, "blob|" + name)>` |
| `devices/<id>.json` | `e2ee/v/<hex HMAC(K_name, "dev|" + id)[:16]>.c` |
| — | `e2ee/vault.json`, `e2ee/README.md` |

- HMAC names hide the document kind (page vs notebook) and the plaintext image hash. The engine needs the real
  doc id back from `delta`: the plaintext of every doc file starts with a small header `{docId, deviceId}` inside the
  ciphertext, and `EncryptingDrive` keeps an id map (in the encrypted DB) filled from its own uploads and from
  downloads. Blob names need no map: the engine fetches blobs by logical name (`ensureBlob`), and the HMAC name is
  computable. `ensureBlob` verifies the sha256 of the decrypted bytes against the logical name.
- Strict path regexes for everything under `e2ee/`; anything else under `e2ee/` is ignored. Items outside `e2ee/`
  are ignored but counted (§7.6).
- **Commit metadata (git)**: when encrypted, author `Slate <slate@invalid>` and message `slate: sync`, with no
  hostname or device id. Plaintext users keep today's messages.

### 5.5 Hostile and broken remote files

- Engine change: a typed `UnverifiableFile` error from `download` is caught by `SyncEngine.pull`, which records one
  notice per sync run ("N synced files could not be verified and were ignored"), marks the item seen and continues
  — one bad file never stops sync.
- Size limits before download: a chunk/snapshot/device record over 64 MiB or a blob over 64 MiB is treated as
  unverifiable without downloading it (git: `git cat-file -s`; OneDrive: the delta item's `size`).
- Snapshot self-check: after each pull, each device checks that its own latest snapshot and chunks it believes
  pushed are present; a missing own file is re-uploaded (the engine's version bookkeeping already knows them).
  Deleted files from *other* devices cannot be restored by us; that device repairs on its next sync.
- **Git hardening (also fixes plaintext sync)**: `core.symlinks=false` in every clone; `GitDrive.upload/download`
  `lstat` the path and refuse anything that is not a regular file, open with `O_NOFOLLOW`, and refuse paths that
  resolve outside the clone.
- `commitAll`'s "device-record-only" filter matches the encrypted device path, and the device record is rewritten
  only when its content changes (not every sync), so the repo does not grow by a commit per sync.

## 6. Lifecycle: unlock, lock, and who may touch the data

### 6.1 One owner of the database

- The app calls `app.requestSingleInstanceLock()`; a second launch focuses the first window and exits.
- The CLIs (`slate-mcp`, `importCli`) open the database only through `openDatabase`. When `vault.json` exists they
  never open it at all: `slate-mcp` proxies to the socket (§9) and the import CLI refuses ("Run the import from the
  app while it is unlocked"). Plaintext users keep today's behaviour.

### 6.2 State machine (`main/vault/`)

`plaintext` | `locked` | `unlocking` | `unlocked` | `locking` | `migrating`.

All services that touch notes (DocStore, BlobStore, search, SyncService, ImportService, external watch, MCP socket
server, conflict list, audit list, theme/updates code that reads settings from the store) are created by one
`openServices(keyRing)` call and reached only through one `services()` accessor that throws `Locked` when there are
none. No module keeps its own reference to `store`.

### 6.3 IPC guard: deny by default

- `ipcMain.handle` is registered **once** at start-up (re-registration throws). Every handler is wrapped: if the
  channel is not in the pre-unlock allowlist and state is not `unlocked`, it throws `Locked`.
- Pre-unlock allowlist: vault status/unlock/quick-unlock/recovery, window chrome, theme-from-preunlock, updates
  status, app version, open-external for the README link. Everything else (including `syncConflicts`, `auditList`,
  `searchQuery`, `onenoteTree`, `blobsCopyImage`, `settingsGet`) is denied.
- The `slate-blob://` protocol handler goes through `services()` and returns 423 when locked. Responses carry
  `Cache-Control: no-store`.
- Menu click handlers call `services()` at click time; menu items that need notes are disabled while locked.

### 6.4 Lock sequence

1. state → `locking`; new IPC note calls get `Locked`.
2. Ask the renderer to flush pending edits (`PageSession` flush) — awaited with a 3 s timeout.
3. Stop emitting renderer events (external batches, sync status) from services.
4. Stop the MCP socket server (finish the request in flight, then close, unlink the socket and token).
5. Ask sync to stop: the engine gets an `AbortSignal` checked between files; await the running sync (a file in
   progress finishes, since its key was taken at the start of that file). Then stop timers and the external watch.
6. Close every DB connection.
7. `keyRing.close()`.
8. **Destroy the BrowserWindow and create a new one** that loads the lock screen (a reload can reuse the renderer
   process and its memory). If Slate wrote the clipboard in the last 2 minutes and it still holds what Slate wrote,
   clear it.

### 6.5 Lock triggers

- Idle: Slate tracks its own last input with `webContents.on('before-input-event')` plus mouse events relayed by
  the renderer (pointerdown/wheel, throttled). Locks when Slate has had no input for the idle time, regardless of
  system idle (which is unreliable under Wayland).
- `powerMonitor` `suspend` (all platforms) and `lock-screen` (macOS, Windows). On Linux, also listen to logind's
  session `Lock` signal over D-Bus by spawning `gdbus monitor --system --dest org.freedesktop.login1` and watching for
  `Lock` on our session (best effort; if `gdbus` is missing, the Security settings say "Screen lock is not detected
  on this system; Slate locks when idle or on sleep").
- Manual: menu "Lock Slate" and Mod+Shift+L.

### 6.6 What is readable before unlock: `preunlock.json`

Contains: theme id, motion, title bar setting, idle timeout, lock-on-sleep, lock-on-screen-lock, quick unlock
enabled. No note content, titles or names. It is MAC'd with K_prefs (`mac` field); a MAC that fails after unlock
means someone edited it while locked: show a warning ("Security settings were changed while Slate was locked") and
restore the values from the encrypted DB, which holds the authoritative copy. Chromium's HTTP disk cache is **off
unconditionally** for Slate (`disk-cache-size=0` is not honoured everywhere; use
`session.defaultSession` with an in-memory partition for the main window: `partition: 'slate'` without `persist:`,
plus clearing the old `Cache`/`Code Cache` once at migration).

### 6.7 Unlock

Password / recovery key / quick unlock → derive (worker) → unwrap MK (local header, then pending) → verify
`check` → unwrap LK from `local-keys.json` → `openServices` → state `unlocked` → the window loads the app. Failed
attempts: no lockout (Argon2 cost is the limiter); after 5 failures show the recovery-key option.

## 7. Migration (opt-in), joining, and remote changes

### 7.1 First device: "Encrypt my notes"

Wizard:
1. Explain protection and loss: a forgotten password **and** lost recovery key means the notes are gone, synced
   copies included. Explain backups/snapshots (§2) and recommend FileVault/LUKS.
2. Every other device must be updated to this version first (if sync is on).
3. If sync is on: **check the remote for `e2ee/vault.json` first.** If one exists, this is a join (§7.3), not a new
   vault. Otherwise continue.
4. Password twice → generate MK, recovery key, vaultId, LK.
5. Show the recovery key (copy / save as text — the save dialog defaults to Documents, never the data folder or a
   synced folder / print). The user must enter the **whole** recovery key (paste allowed); Slate then does a real
   unlock round trip with it (derive → unwrap MK → check) before continuing.
6. If sync is on: **claim the remote** (§7.2 steps 1–3) before touching local data, so a concurrent enable on
   another device loses the race cleanly and joins.
7. Local migration (§7.4), then remote re-upload (§7.2 step 4).

### 7.2 Claiming and wiping the remote

1. Run one plaintext sync so nothing local is unpushed; record the fetched origin sha.
2. **git**: in a fresh temporary clone directory, build an orphan commit holding only `README.md` ("end-to-end
   encrypted by Slate; Slate 0.1.x cannot read it"), `e2ee/README.md` and `e2ee/vault.json`, and
   `git push --force-with-lease=<branch>:<recorded sha> origin HEAD:<branch>`. If the lease fails: fetch; if the
   remote now has `e2ee/vault.json` → join it (§7.3); else re-run step 1 and retry (at most 3 times).
   **OneDrive**: upload `e2ee/vault.json` with a conditional create (`@microsoft.graph.conflictBehavior=fail`); on
   conflict → join. Then delete `docs/`, `blobs/`, `devices/` and tell the user to empty the OneDrive recycle bin
   (version history cannot be purged by Slate).
3. Delete **every** clone under `git-sync/` (one per past remote) and re-clone the new branch. No `gc` tricks.
4. After the local migration: reset sync bookkeeping (`sync_meta` cursors and version vectors, `sync_seen`,
   `blob_synced`) inside the encrypted DB, so the next sync pushes every document and blob through
   `EncryptingDrive`. Loro imports are idempotent, so re-pushing cannot duplicate content.

### 7.3 Joining an encrypted remote

- Every sync run, **before any upload** (the OneDrive path uploads before `delta` today: reorder so the vault check
  comes first), the drive checks `e2ee/vault.json` (git: after fetch, read from `origin/<branch>` with
  `git show`, before rebasing anything).
- A `plaintext` device that finds a vault stops syncing and shows "Your notes are now encrypted on another device.
  Enter your password to keep syncing." Join: password or recovery key → unwrap MK from the remote header → local
  migration (§7.4) with that MK (new LK for this device) → delete all clones and re-clone → reset bookkeeping →
  sync. Local edits are kept and pushed (Loro merges them).
- A new device setting up sync against an encrypted remote asks for the password right after the remote URL and
  creates its database encrypted from the start.
- Enabling sync *later* on an encrypted device: if the target remote is plaintext and non-empty, the setup offers
  "Encrypt this sync folder (replaces its history)" → §7.2; if it is empty → write the vault and push; if it has a
  vault with another `vaultId` → join it (rewrap LK; the old local vault's recovery key stops applying, the wizard
  says so) or cancel. Switching remotes is the same flow.

### 7.4 Local migration (resumable)

Progress is recorded in `migration.json` (local only) as `{ step, vaultId, dbFile }`; each step is idempotent and
re-runnable. Before step 1 the app must be the only holder (§6.1): close all services (as in §6.4 steps 2–6) and
keep the plaintext DB open with `PRAGMA locking_mode = EXCLUSIVE` for the copy.

1. Write `vault.json` (if not joining, created in §7.1) and `migration.json` atomically.
2. `PRAGMA wal_checkpoint(TRUNCATE)` on `slate.db`, then copy `slate.db` to `<dbFile>.tmp`. On the copy (plaintext,
   opened alone): `PRAGMA journal_mode = DELETE`; `PRAGMA cipher='sqlcipher'`; `PRAGMA legacy=4`;
   `PRAGMA rekey = "x'<hex LK>'"` (rekey works on a non-WAL plaintext DB — verified by the reviewer that it refuses
   in WAL mode); close.
3. Move images: insert every file from `blobs/` into `blob_data` in the copy, verifying each sha256 equals its name.
4. Open the copy **with `openDatabase`** (the runtime path) and verify: `PRAGMA integrity_check` = ok, per-table row
   counts equal the plaintext DB's, every doc loads with Loro, `blob_data` has every image. Then
   `PRAGMA journal_mode = WAL`; close; fsync; rename `<dbFile>.tmp` → `<dbFile>`.
5. Write `local-keys.json` (wrapped LK + `db: <dbFile>`) atomically — **this is the switch**. From here the
   encrypted DB is authoritative.
6. Cleanup: unlink `slate.db`, `slate.db-wal`, `slate.db-shm`, the `blobs/` folder, Chromium `Cache` and `Code
   Cache`, stale `slate-one2html-*` temp folders; remove `migration.json`.

Crash before step 5: the plaintext DB is authoritative; on start the app sees `migration.json`, deletes
`<dbFile>.tmp` and resumes from step 2 (vault and keys are already known only if the user re-enters the password —
the wizard re-asks it; MK is recovered from `vault.json` with the password). After step 5: resume cleanup only.
Tests inject a crash between every step (an env hook only honoured when `SLATE_E2E=1`).

### 7.5 Two devices enabling at once

The claim (§7.2 step 2) happens before any local change, so the loser simply joins the winner's vault; it never
creates a second recovery key that works. If a device somehow finished a local migration under its own vault and
then finds another vault on the remote (e.g. it was offline), "join" rewraps its LK under the remote MK (LK makes this
cheap) and discards its own vault after the user enters the remote vault's password.

### 7.6 Old Slate versions

0.1.x knows nothing of `e2ee/`. A fresh 0.1.x clone of the new branch would re-push plaintext under `docs/`. New
versions: ignore `docs/`, `blobs/`, `devices/` once encrypted, show a persistent warning "A device running an older
Slate is writing unencrypted notes to your sync folder — update it", and remove those paths from the tree in their
next commit (not from history). The wizard and release notes tell users to update every device first.

## 8. Quick unlock

- Enable (needs the password once): random 32-byte `QU` → `safeStorage.encryptString` → `quick-unlock.bin`
  together with `wrap(MK, KEK_qu = HKDF(QU, info="slate/v1/quick"), AAD = "slate-qu/v1|" + vaultId + "|" +
  deviceId)`.
- macOS: available when `systemPreferences.canPromptTouchID()`; unlock = `promptTouchID` → decrypt QU → unwrap MK.
  Because the ad-hoc signature changes with each release, macOS may ask to allow Keychain access after an update, or
  decryption may fail if the user clicks Deny: any failure falls back to the password silently ("Touch ID
  unavailable, enter your password"), and offers to re-enable after a successful password unlock.
- Linux: only when `safeStorage.getSelectedStorageBackend()` is `gnome_libsecret` or `kwallet*` (never
  `basic_text`); the lock screen shows a one-click "Unlock" button.
- Settings text: "Touch ID / keyring unlock is a convenience. Programs running as you can read this key without
  Touch ID; your password protects a stolen, powered-off computer."
- Disabled and deleted on vault change (join), and on "Forget quick unlock".

## 9. MCP access through the app

- When encrypted, the MCP tools (`createSlateMcpServer` from `@slate/mcp`) run **inside the app**, over the real
  `DocSource` with the app's permission checks and audit writes. The app listens on a Unix socket only while
  unlocked; `slate-mcp` becomes a byte proxy: stdio ↔ socket, no parsing. A client cannot call `DocSource`
  directly, cannot write raw Loro updates and cannot forge audit rows.
- Socket path: `<userData>/mcp.sock` when its length is ≤ 100 bytes, else `$TMPDIR/slate-<uid>/mcp.sock` in a
  directory created with mode 0700 (checked owner and mode before use). The data folder is chmod 0700. A stale socket
  file is unlinked on start. No token file: the 0700 folder is the boundary; same-user processes are out of scope (§2).
- Locked or not running → the proxy answers each MCP request with an error result "Slate is locked or not running.
  Unlock Slate to give AI access."
- `externalWatch` stays (SyncService and the importer write through their own connections, and pulled updates reach
  the renderer through it). MCP writes now happen in-process; they are emitted through the same `ExternalBatch`
  path.

## 10. Settings → Security

A registry section "Security" (`shared/settings/schema.ts` entries for every key):
- Status + *Encrypt my notes…*.
- Change password (current password or recovery key) → new wrap, `revision + 1`, upload header.
- New recovery key (needs password) → new wrap, `revision + 1`. Text from §4 about old copies.
- Lock after idle: 5 / 15 / 30 (default) / 60 min / 4 h / Never. Lock on sleep (on). Lock on screen lock (on;
  "not detected on this system" note where applicable). Lock now.
- Touch ID (mac) / Remember in system keyring (Linux).
- "AI access works only while Slate is unlocked."

## 11. Left out of v1

- Re-encrypting everything under a new MK (the real fix for a leaked old password + ciphertext copy). The design
  keeps this possible: K_sync/K_name derive from MK, a future "rotate" writes a new vault id and re-uploads.
- Decrypting back to plaintext. WebAuthn/PRF, Secure-Enclave keys (need a signed app).

## 15. v3 amendments (second review; these override earlier sections where they differ)

- **N1 Remote names: reversible, no map, no in-ciphertext header.** Every doc id is `notebook:<uuidv4>` or
  `page:<uuidv4>`, and device ids are uuidv4 (verified in code: `crypto.randomUUID`). A remote name is
  `hex(AES-256-ECB_single_block(K_name_enc, packed))` where `packed` is the 16 UUID bytes with the version nibble
  replaced by a kind code (1 = notebook, 2 = page, 3 = device); variant bits stay. Inputs are unique, so a single
  block of a PRP leaks only equality (which the folder structure already shows). `K_name_enc = HKDF(MK,
  info="slate/v1/name-enc")`. Decoding: decrypt the block, read the kind, restore version nibble 4, and **reject** if
  the variant bits are not `10` or the kind is unknown (a forged name decodes to garbage and is ignored). Any id that
  is not kind + uuidv4 is refused at upload (assertion) — migration verifies all existing doc ids first and aborts
  with a clear error otherwise. Remote paths: `e2ee/d/<docName>/<devName>/<seq>.c` and `s-<seq>.c`,
  `e2ee/v/<devName>.c`, blobs `e2ee/b/<hex HMAC(K_name, "blob|"+name)>` (fetched by computed name only).
  The envelope AAD binds the **engine (logical) path**, which `delta` reconstructs from the decoded names before
  download — so the engine's own-device skip and `seen` work without downloading. The §5.4 id map and doc header are
  dropped.
- **N2 Header writes**: every change is built on the highest *verified* header this device has (local or pending),
  with `revision = max + 1`. `vault.json` is only ever written remotely by compare-and-swap: git — the commit is pushed
  alone; on rejection, fetch, re-verify, rebuild on the new highest, retry (on a rebase conflict in `e2ee/vault.json`
  take theirs and rebuild); OneDrive — upload with `If-Match: <eTag>`, on 412 re-download and rebuild.
- **N3 Exclusive hold**: `PRAGMA locking_mode = EXCLUSIVE; BEGIN IMMEDIATE; COMMIT;` on the plaintext connection,
  kept open for the copy. `SQLITE_BUSY` → stop with "Another program has your notes open (for example an AI agent's
  slate-mcp). Close it and try again."
- **N4 Session**: keep the default session (so `localStorage` and `protocol.handle` keep working). HTTP disk cache
  off with `app.commandLine.appendSwitch('disk-cache-size', '1')` unconditionally, and `session.clearCache()` +
  `clearCodeCaches` at start when encrypted. (localStorage holds only ids/widths/colours — audited.)
- **N5 MCP proxy**: the proxy contains a minimal MCP responder used only when the app is unreachable: answers
  `initialize` itself (caching the client's `initialize` request), returns an empty-ish `tools/list` with one tool
  description "Slate is locked", and an error result for `tools/call`. When the socket becomes reachable, it
  connects, replays the cached `initialize` (+ `notifications/initialized`), discards the replayed responses, and
  then pipes bytes. After an app lock (socket closed) it reconnects on the next request the same way. Tested in E6.
- **N6 Window recreation**: create the lock window first, then destroy the old one; `window-all-closed` ignores
  windows closed while state is `locking`.
- **N7 Linux screen lock**: find our session with logind `GetSessionByPID`; watch its `LockedHint` property
  (`gdbus monitor --system`) and the session bus `org.gnome.ScreenSaver.ActiveChanged` /
  `org.freedesktop.ScreenSaver.ActiveChanged`. Kill monitors on quit. Missing tools → the settings note.
- **N8 Argon2**: a fresh worker per derivation, terminated after (WASM memory is never returned). Parameters
  256 MiB × 4 passes (~0.6 s on Apple Silicon); calibrate towards ~1 s target, never below the floors. RFC 9106 vectors
  only if hash-wasm supports `secret`/`ad`; otherwise reference vectors without them (e.g. from the `argon2` CLI /
  libsodium test outputs embedded as constants).
- **N9 KeyRing.get()** returns a fresh copy (`Buffer.from(key)`) or a `KeyObject`; callers drop it after use.
- **N10 Aborted migration**: start-up state "vault present, no `local-keys.json`, plaintext DB authoritative" =
  `migrating`: the app opens plaintext as before and shows "Finish encrypting your notes" (asks the password,
  resumes) and "Cancel encryption" (deletes local vault files; if the remote was claimed the device becomes a joiner
  on its next sync). Step 3 images are inserted into the copy **before** `rekey` (one keyed open, in step 4).
- **N11**: authenticate before inflating; cap inflated output at 256 MiB. Refuse images over 64 MiB when added
  (paste/import), with a message.

## 16. Compliance profile

**Precedence.** `docs/reviews/compliance_audit.md` (`SLATE-CA-2026-10-23`) amends this spec. Where the two disagree,
the audit wins. The maintainer's answers to its decisions are in `docs/compliance/decisions.md`.

- **Profiles (audit §4.1).** Two crypto profiles: `standard` (Argon2id, as above) and `fips-140-3` (PBKDF2 per
  SP 800-132, OpenSSL FIPS Provider 3.1.2, stricter lock and password policy). The wizard offers the FIPS profile
  only in builds that bundle the FIPS provider.
- **Self-test (§4.2).** A power-up self-test runs before any key is used. Any failure enters `selftest-failed`, a
  terminal state that blocks every user, encrypted or not.
- **Memory (§4.3).** Keys live in the native module's secure heap as handles. JavaScript sees handles, and secrets
  cross IPC as bytes, never strings.
- **Electron boundary (§4.4).** Navigation and window-open guards, IPC sender validation, a permission policy and a
  production CSP.
- **Formats (§4.5, §4.6).** Header v2, `SLE2` envelopes and SIV-style names under suite 0x02 replace AES-ECB names
  for new vaults. v1 files stay readable.
- **Rotation (§4.7).** Key epochs. Converting a vault to v2 or to `fips-140-3` is offered in Settings, never done
  automatically.
- **Audit events (§4.8)** are logged without secrets.
- **Native build (§4.9).** `@slate/native` statically links OpenSSL 3 and loads the unmodified FIPS provider.

**Status (final, 0.2.0).** C0 to C13 are implemented. The statements below replace the list above where they differ.

- **What is claimed** is exactly audit §1.2 and nothing more: the `fips-140-3` profile's note-protecting operations run in
  the OpenSSL FIPS Provider 3.1.2 (CMVP #4985) in approved mode, with a power-up self-test, a terminal error state and
  key destruction at lock. Slate itself is not FIPS 140-3 validated and is not FedRAMP authorized (D-3, D-5). Transport
  TLS is outside the module (POAM-11).
- **Self-test** runs 19 known-answer tests before any service answers, from Settings, and before every vault change.
- **Rotation, upgrade, conversion (C9)** are offered in Settings → Security once every device record reports 0.2.0 or
  newer (D-7), and never run on their own.
- **Where to read next:** `docs/compliance/security-policy.md` (module consumer policy), `poam.md` (open items),
  `key-inventory.json`, `traceability.yaml`, `release-checklist.md` (gates before a release).
