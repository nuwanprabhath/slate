# Plan of action and milestones (POA&M)

Open items from `docs/reviews/compliance_audit.md` (SLATE-CA-2026-10-23) that the implementation cannot close
on its own. Each row says what is missing, what is in place meanwhile, and what closes it.

| Id | Control / rule | Weakness | In place meanwhile | Closes when | Owner | Opened |
| --- | --- | --- | --- | --- | --- | --- |
| POAM-01 | CM-14 (signed components) | The macOS build is ad-hoc signed and not notarised; the Linux `.deb` and AppImage carry no package signature (D-1 = not now). | Update feeds and every artefact carry an Ed25519 signature that the app verifies against a pinned key before it offers, downloads or installs an update (`update/signature.ts`, `scripts/sign-update.mjs`). Signing switches on from secrets with no code change: `MAC_CSC_LINK` + `MAC_CSC_KEY_PASSWORD` (Developer ID), `APPLE_ID` + `APPLE_APP_SPECIFIC_PASSWORD` + `APPLE_TEAM_ID` (notarisation), `LINUX_SIGNING_KEY` (OpenPGP `.asc` per package). | The maintainer obtains an Apple Developer ID and a Linux package-signing key and adds the secrets; the next release is signed and notarised. | Maintainer | 2026-10-23 |
| POAM-02 | SI-7(15) (code authentication) | The operating system cannot authenticate Slate's code before it runs: no Developer ID signature or notarisation on macOS, no package signature on Linux, and no ASAR integrity on Linux (B-7). | ASAR integrity on macOS (fuse); the signed update feed and artefact signatures (B-7's compensating control on Linux); `scripts/check-fuses.mjs` fails a release whose fuses differ from `electron-builder.cjs`. | As POAM-01. | Maintainer | 2026-10-23 |
| POAM-03 | Z-9, macOS part (SC-4, SC-39) | Without a Developer ID there is no hardened runtime, so another non-root process can attach to Slate and read key material. | `build/entitlements.mac.plist` has no `com.apple.security.get-task-allow`; `electron-builder.cjs` turns the hardened runtime on whenever a certificate is present. On Linux Z-9 is unaffected (`prctl(PR_SET_DUMPABLE, 0)`, C2). Since C7 the POST runs `hardenProcess` first on every platform: no core file on macOS either (RLIMIT_CORE 0), and a packaged build that cannot harden itself does not start. | As POAM-01: the first build signed with a Developer ID runs under the hardened runtime. | Maintainer | 2026-10-23 |
| POAM-04 | B-6 / F-EL-02 (`runAsNode` fuse) | The release fuse `runAsNode` stays on: the packaged `slate-mcp` launcher runs the app binary with `ELECTRON_RUN_AS_NODE`. A Node SEA was not built: Node 22 (the repo's and CI's Node) needs `postject` to inject the blob, which is not a dependency, and with no vault `slate-mcp` opens SQLite through the Electron-ABI `better-sqlite3-multiple-ciphers` build, which a SEA cannot load. | `enableNodeOptionsEnvironmentVariable` and `enableNodeCliInspectArguments` are off in releases, so `ELECTRON_RUN_AS_NODE` gives a plain Node with no extra flags; with a vault, `slate-mcp` is a byte proxy to the app's 0700 socket and never sees keys. | `slate-mcp` ships as its own executable: either a SEA of the byte proxy (with plaintext data served by the app's socket as well), or a Node 25+ `--build-sea` build; then `runAsNode: false` and `releaseConfig.test.ts` flips. | C12 follow-up | 2026-10-23 |
| POAM-05 | T-UPD-02 (key rotation) | Only the current update-signing key is pinned. | The verifier accepts any key in `PINNED_UPDATE_KEYS` and the signer refuses a key the app does not pin, so adding the next key is a one-line change. | The maintainer generates the next Ed25519 key pair offline and its public key is pinned in a release before the current key is retired. | Maintainer | 2026-10-23 |
| POAM-06 | SI-7, SR-11 (update freshness) | Signed feeds carry no expiry or counter, so someone controlling the GitHub release can withhold updates (freeze) or keep offering an older signed release that is still newer than the installed one. | Rollback below the running version is refused (`verifier.ts`: only a strictly newer signed release is accepted); every update needs a valid signature from a pinned key. | Feeds carry a signed expiry (and the app warns when the newest feed it can get has expired), or releases move to a transparency log. | C12 follow-up | 2026-10-23 |
| POAM-07 | D-1 + §4.9 (FIPS provider under a Developer ID) | Signing changes `fips.dylib`'s bytes, which breaks both the pin compiled into `slate_native.node` and the module's own `module-mac`; and the hardened runtime's library validation refuses a provider that is not signed by the same team. So the first Developer ID build cannot start the module as built today. | Signing is off (D-1), and `electron-builder.cjs` excludes `Resources/fips/` from re-signing (`signIgnore`), so the shipped provider is byte-for-byte the pinned one. `release.yml` runs `scripts/smoke-native.cjs` inside the packaged binary and refuses to publish unless it reaches approved mode. | When D-1 is turned on, re-verify: (1) sign `fips.dylib` once with the Developer ID (hardened runtime) **before** `fipsinstall`, keep that signed file as the build artefact rather than rebuilding it (signatures carry timestamps, so a rebuild never matches), and commit its digest to `fips-digest.json`; (2) the smoke check passes on the signed `.app`; (3) the lab confirms under L-3/L-4 that the signed file is the validated module; (4) `slate_native.node` itself is covered by the bundle signature (today nothing authenticates it: it sits in `app.asar.unpacked`, outside the asar integrity fuse). | Maintainer + C2 follow-up | 2026-10-24 |
| POAM-08 | Z-1 / Z-7 (Argon2id working memory) | The Argon2id memory matrix (256 MiB by default) is far larger than the module's 1 MiB locked secure heap, so libcrypto allocates it in ordinary memory (patched `argon2.c`, C4): it is not mlock'd and can be paged to swap while a derivation runs. | The matrix is cleansed before it is freed (`OPENSSL_secure_clear_free` cleanses a pointer outside the secure heap, then frees it); matrices that fit stay in the secure heap; the derivation runs on a libuv thread from a secure-heap copy of the password, which is wiped when the job ends; before C4 the same matrix sat in hash-wasm's WebAssembly memory and was never wiped. Full-disk encryption of the swap (macOS default; recommended on Linux) protects what is paged. | The matrix is allocated with `mmap` + `mlock` (and `MADV_DONTDUMP`) inside the module when RLIMIT_MEMLOCK allows, falling back to the current path and reporting it (C7). | C7 | 2026-10-24 |
| POAM-10 | Z-11 / Z-5 (typed secrets in main), SC-4 | Narrowed by phase 12 (MEM). T-ZERO-04's first CI run found the password's UTF-8 bytes in main after lock. They were not Electron's IPC message: they were Slate's own copy for the module, `new Uint8Array(password)` in `vault/kdf.ts` (and `recovery.ts`), which V8 kept on its heap because it is short; when the addon read it V8 moved the bytes to a new store, the module wiped that one, and the heap copy stayed behind as garbage. `moduleCopy` (`shared/secret.ts`) now gives the module its own ArrayBuffer, and T-ZERO-04 finds no copy of the password (or any key) in main after lock. What remains: the Mojo message that carries the secret to main is freed by Chromium without being cleansed and no JavaScript can reach it (not seen by the scan after lock, but not ruled out at other times), and the renderer's DOM field and V8 strings until the lock window's process exits (Z-6). | Main zeroes every copy it can reach on every exit (`secretHandler`, `src/main/vaultIpc.ts`; `vaultIpc.test.ts`) and hands the module only `moduleCopy` copies (`tools/guards/vaultSecrets.test.ts`); the preload and page zero theirs; the lock window's renderer process exits after unlock (Z-6); Linux main is non-dumpable and no process leaves a core file (Z-9). T-ZERO-04 (`e2e/memory.linux.ts`, Linux CI) holds the password to the same zero-hit rule as the keys. | Upstream: a cleansing allocator for IPC message payloads in Electron/Chromium, or a secret channel outside structured clone. | C7 follow-up | 2026-10-26 |
| POAM-11 | SC-8, SC-8(1), F-NIST-10, audit §1.4 M-19 (transport TLS) | The TLS that sync and sign-in use is outside the validated boundary: git's TLS or SSH, and Electron's Node `fetch` (BoringSSL) for Microsoft Graph. OAuth tokens and git credentials depend on those stacks. Accepted risk. | Note content is sealed (`SLE1`/`SLE2`) before it reaches the transport, so SC-8(1) holds for content. Recorded in the OSCAL component's remarks. | Maintainer | 2026-10-24 |

| POAM-15 | SC-12, SI-7 (vault rollback within an epoch; review C9 L6) | Deleting `vault.seen.json` makes the sync check's offline-change branch fall back to the remote's own header, so a same-epoch password-change overwrite becomes possible while the device is offline. | POAM-16 | Z-6 / Z-9 (the lock window's renderer on Linux), SC-39 | Narrowed by phase 12 (SANDBOX), maintainer decision 2026-10-26 "Force setuid sandbox; AppImage warns". The lock window's renderer holds the typed password until it exits (Z-6), and `hardenProcess` reaches main only, so its protection is Chromium's sandbox. **The .deb** now always launches with `--disable-namespace-sandbox` on the real command line (the desktop entry through `deb.executableArgs`, the `slate` command through the `/usr/bin/slate` wrapper the after-install writes; the after-install makes chrome-sandbox root 4755 and fails the install if it cannot), so its renderers run the setuid sandbox: seccomp-bpf and non-dumpable, whether user namespaces are allowed or not. Measured on linux-arm64 packages in the Ubuntu 24.04 Docker harness: lock renderer `Seccomp: 2`, `/proc/<pid>/mem` uid 0, in the init user namespace, for both launch paths with `user.max_user_namespaces=0` and with namespaces allowed (control: the bare binary with namespaces allowed gives mem uid 1000). **Residual: the AppImage** still runs without the sandbox where `unshare -Ur` fails (Ubuntu 23.10 and later; measured: `--no-sandbox`, `Seccomp: 0`, mem uid 1000), and with the user-namespace sandbox (sandboxed, dumpable) where namespaces are allowed. | The .deb's flag and setuid helper are guarded (`tools/guards/debSandbox.test.ts`). When a renderer runs unsandboxed (`--no-sandbox` on the command line, or on Linux a live renderer whose `/proc/<pid>/status` shows Seccomp other than 2; `src/main/rendererSandbox.ts`), the lock screen shows a small line and Settings → Security a notice (dismissable once, `sandboxNoticeDismissed`) saying other programs running as the user can read its memory, a typed password included, and recommending the .deb; `app.renderer.unsandboxed` goes to the security log once a run (`e2e/settings.spec.ts` POAM-16 tests; seen in the packaged AppImage). CI runs Linux e2e in the setuid sandbox, and T-ZERO-06 (`e2e/coredump.linux.ts`) fails on an unsandboxed or dumpable renderer. README "Keys in memory" recommends the .deb. | Stop shipping the AppImage, or ship it only with a working setuid sandbox (it cannot carry a setuid helper), or set the renderer's core limit and dumpable flag from main (a new addon call; covers core dumps, not ptrace). | Maintainer | 2026-10-26 |
